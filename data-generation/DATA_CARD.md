# Data Card — Synthetic WC Bill Corpus

## What this is

A fully synthetic dataset of workers' comp medical bills, generated by
`generate_bills.py` against the reference rule tables built by
`reference/build_reference_data.py`. Every patient, provider, claim, date,
and dollar amount is generated by a random-number generator. **No real
claims, bills, providers, or patients — from any employer, past or
present — appear anywhere in this dataset.** Only the coding *rules* the
generator checks against (CPT/HCPCS and ICD-10-CM code numbers, NCCI PTP
edit relationships, MUE unit thresholds) are drawn from real, public
coding conventions — see `reference/build_reference_data.py`'s module
docstring for exactly which rows are CMS-documented vs. illustrative.

## Generation logic

1. **Reference rule engine** (`wc_bill_review.db`, loaded from the 4 CSVs
   in `reference/`): 44 CPT/HCPCS codes, 21 ICD-10-CM codes across 9 body
   regions, 12 NCCI PTP edit pairs, 44 MUE unit thresholds.
2. **Clean bill construction**: for each bill, the generator picks a body
   region, a matching diagnosis code, a synthetic patient and provider, an
   injury date and date of service (0-150 days apart, bucketed into
   early/mid/late stage), and a care pathway (E/M only, E/M + therapy,
   therapy only, injection, imaging, or a surgical episode) chosen to be
   consistent with the provider's specialty and the injury stage. A
   synthetic "documentation level" (1-5) is sampled, and the E/M code
   billed is always the one that level supports. Every clean bill is
   checked against all four rule types before being accepted — if
   construction accidentally produced a rule violation, it's discarded
   and regenerated rather than kept and mislabeled.
3. **Violation injection**: for the ~20% labeled-anomalous bills, the
   generator builds a fresh clean bill and then mutates it to break
   *exactly one* rule:
   - **unbundling** — injects both codes of a real NCCI PTP edit pair
     (preferring a pair native to the bill's own body region) with no
     bypass modifier.

   Separately, clean bills that legitimately assemble both codes of a
   modifier-eligible NCCI pair (most often two PT/OT codes sampled
   together, e.g. 97110 + 97140) resolve one of two realistic ways:
   ~35% keep both lines and attach modifier `59` to the bundled code
   (a documented, distinct-procedure bypass — still clean), the rest
   simply drop the bundled line. This is what gives the "modifier usage
   patterns" feature (WK2.2) real signal: modifier `59` present on a
   line is associated with clean bills, the same code pair present with
   no modifier is what the unbundling label means. A bill can carry both
   a legitimate bypass on one pair and an injected violation on a
   different, unrelated pair at the same time — the label only names the
   actual violation.
   - **fragmented_billing** — pushes one line's units 2-6 over its MUE
     cap.
   - **causality_mismatch** — swaps the diagnosis to a code from a body
     region unrelated to any procedure on the bill.
   - **upcoding** — bills the top E/M complexity code while dropping the
     synthetic documentation level to 1-2 (supports at most a level-3
     visit).
   After mutation, the bill is re-checked and only kept if it trips
   *that one* rule and no others — so every `anomaly_types` label is
   exact, not approximate.
4. **Split**: default 80% clean / 20% violation, violation bills spread
   evenly across the four types (200 each at n=4000).

## Output files (`output/`)

- `synthetic_bills.jsonl` — one JSON object per bill (full structure,
  including per-line units/charges and `anomaly_details` explaining
  *why* an anomalous bill was flagged, in plain language, citing the
  rule that was broken).
- `synthetic_bills_flat.csv` — the same data flattened for quick
  spreadsheet/EDA use.
- `generation_stats.json` — actual counts and the RNG seed used, for
  reproducibility.

## Known limitations / scope choices

- **44 CPT/HCPCS codes and 21 ICD-10-CM codes**, not the full ~10,000+
  and ~70,000+ code universes. The subset covers E/M, PT/OT, common
  orthopedic surgery, fracture care, injections, casting, and imaging —
  enough breadth to exercise every rule type across 9 body regions, not
  a full specialty-by-specialty catalog. `head` (concussion) intentionally
  has no procedure pool beyond E/M — cognitive/vestibular therapy codes
  are out of scope for this pass.
- **12 NCCI PTP edit pairs**: 5 are long-documented, stable bundling
  relationships; 7 are illustrative pairs built on the same real edit
  *patterns* (same joint/same session bundling) rather than verified
  against a specific current-quarter CMS file. See the source column in
  `reference/ncci_ptp_edits.csv`.
- **MUE unit thresholds** follow well-documented CMS conventions for
  these code families (single surgical procedures = 1/day, ~15-minute
  timed therapy codes ≈ 4/day) rather than a parsed current-quarter MUE
  file. Exact values can shift by a unit or two quarter to quarter.
- **No network access to cms.gov from this build environment** is the
  reason for the two points above — this environment cannot download the
  live CMS NCCI PTP / MUE quarterly release. The reference CSV shapes
  were designed so that swapping in a real parsed extract later is a
  drop-in replacement, not a rewrite.
- **Billed amounts are entirely synthetic** — a hand-set base fee per
  code with random jitter and a per-provider "billing intensity"
  multiplier (for the peer-deviation feature planned in WK2). They are
  illustrative only and not modeled on any real fee schedule.
- **One diagnosis code per bill** in this pass (real bills often carry
  several); the generator supports adding a second, non-conflicting
  diagnosis in a later revision if the model needs it.
- **Violation types are mutually exclusive by construction** (each
  anomalous bill trips exactly one rule). Real bills can obviously have
  more than one problem at once; multi-violation bills are a reasonable
  WK2 stretch addition, not included in this first pass.

## Reproducing

```bash
cd data-generation
python3 reference/build_reference_data.py   # writes reference/*.csv
python3 reference/load_reference_db.py      # builds wc_bill_review.db
python3 generate_bills.py --n-bills 4000 --seed 42
```

All three steps are deterministic given the same seed.
